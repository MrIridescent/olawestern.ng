What this is, for the non-technical reader. The campaign has a website that its own staff update without an engineer, and that refuses — in code, not in policy — to publish any claim about a real person unless a link to a published report is attached to it. Today that grade is 40 out of 100, because four published lines do not yet have their evidence documents, and nobody was willing to invent one. §1 — THE TWO DEFINING IDEAS

One rule the server enforces, one surface the public page is

Everything else in the platform is in service of these two commitments, or of the environment they operate in: a low-data, phone-first electorate, a data-protection statute that just came into force, and a rival campaign with an incentive to quote the site back at it.

The publish gate

VERIFIED — asserted by scripts/check-cms-gates.mjs, E2

  • No track-record entry or Truth Room ruling can be created without an evidence link to the published report or document that proves it. Enforced server-side on POST /api/admin/record and POST /api/admin/fact-checks — not in the form, not in the UI.
  • The evidence link may be replaced but never emptied: PATCH refuses a blank. Softening a claim in place is not the same decision as taking it down.
  • DELETE (or unpublish) is the only takedown, and for seed-owned rows it records a tombstone so no future content bundle can resurrect the withdrawn line.
  • Enforcement lives in EVIDENCE_RULE (src/lib/cms.ts). One sentence everywhere, so the campaign learns one rule instead of one rule per endpoint: “A public claim about a real person needs its evidence: paste the link to the published report or document that proves it.”
  • Rows published before the gate existed stay editable (refusing a typo fix would keep a wrong sentence live) but are graded block by the site’s own audit until they carry a report — see §4.

“Unsourced” is a state the software refuses, not a standard people are reminded of. (01-PRD FR-1 · ADR-008, era P5)

The Live Desk

VERIFIED — browser-verified 3 Nov 2026 (E4); two interactions untestable, see §10: scroll-follow of the rings and screenshot-level visual parity are verified by reading, not observation

  • The public page is the CMS. ⌘E reveals 38 annotated data-ow sites as rings on the live page; tap-to-edit opens a sheet prefilled with the rendered value; 25 field specs across 5 field kinds (text · area · url · choice · boolean) map each tapped attribute to the admin route that already validates it.
  • ⌘K command deck parses a pasted link into an intent (publish this clip / cite this source / jump). It does not generate content — there is no model in the editing layer (ADR-013).
  • ⌘Z replays the same route with the previous value. In-memory, per-session; the durable history is the backup.
  • After every write: same route, same validation, same refusal wording, then revalidatePath() on the server and router.refresh() in place — the page the desk is standing on redraws without a reload or lost scroll position.
  • Anonymous visitors receive zero DOM: the overlay probes GET /api/admin/login; a cookie-less probe renders no dock, no rings, no listeners, nothing in the server HTML. An unfinished sentence is never advertised to the other side.

No second admin UI to drift. “The cost of a website in a campaign is not the build; it is the twenty-six small changes between the build and the election.” (06-USE-CASES B4 · FR-7…FR-13)

§3 — ARCHITECTURE, AS DRAWN

One store interface over two interchangeable backends

Drawn from divs and rules, the way the system is actually shaped: a small, mostly-read, bursty, mobile-heavy public site with a tiny writable state and an image folder that grows. That is a storage-and-bandwidth problem, not a compute problem. (11-HARDWARE §1 · ADR-001/002/026)

Storage growth note

The axis of growth is photographs, not rows. db.json stays under 1 MB even at 30,000 volunteer records — the row count is the compliance concern, not the byte count. A desk that photographs a rally on a phone produces 3–4 MB per frame; 500–2,000 uploads project to 1–8 GB against a 20 GB minimum disk. There is no resize step because sharp was deliberately excluded (ADR-017) — if uploads go daily, the honest fix is object storage or edge optimisation, not a bigger box. (11-HARDWARE §5)

Honest footnote — what is not in the box

  • No middleware — the auth check is per-route and forgettable; it constrains which hosts are possible and moves rate limiting and IP allowlists to the edge.
  • No ORM, no raw SQL path in the file store; the Supabase client is parameterised by construction.
  • No test framework — the gate script plus type check plus build replace it (§10).
  • No .git — the folder is not yet a repository; rollback by revert is currently impossible. BLOCK
  • No queue, cron, worker, analytics, object-storage SDK or output:'standalone' in the current build.

§4 — THE INTEGRITY RAIL

How the site grades itself — and why 40 is honest

GET /api/admin/health recomputes the live store into a 0–100 score, a ready boolean and findings weighted by severity, each carrying the offending sentence’s page and data-ow key so a finding is a to-do, not a description. It grades content, not tool usage, so it cannot be farmed by editing more. VERIFIED E2, 3 Nov 2026

score  =  max(0, min(100,  100 − Σ  min( WEIGHTS[sev] × max(1, ⌈count/3⌉),  WEIGHTS[sev] × 3 ))
WEIGHTS  =  { block: 18,  warn: 7,  info: 2 }
observed  =  100 − (18 + 18) · block  − …  =  40  ·  ready: false · 6 findings · 4 block lines

The grouping (ceil(count/3)) and the per-severity cap (weight × 3) mean a hundred unsourced claims cost the same 54 points as three, and deleting the single worst line buys no score. The metric is designed to be hard to satisfy and impossible to grind upward by cosmetic edits. (01-PRD FR-2 · ADR-014 · src/lib/liveDesk/integrity.ts)

The publish-gate ruleset, three lines

  1. Evidence on creation, server-side. POST refuses a row whose report link is absent, non-http(s), or a javascript: URL. Asserted twice by script.
  2. Immutable once attached. PATCH may replace the link; it can never blank it. This closes the “soften the claim in place at 22:00” path — the panic path a desk actually takes.
  3. Takedown is one honest act. DELETE/unpublish only, with tombstones so re-synced bundles cannot resurrect withdrawn rows. The rail grades pre-gate lines block rather than grandfathering them.

Why full serverless is not sufficient as the code stands

  • The mutating admin routes need a persistent writable disk: data/ is gitignored, so a deploy-as-is serverless build reseeds from bundle content and silently deletes every collected volunteer lead; writes that do land go to an ephemeral lambda filesystem and vanish on the next cold start (11-HARDWARE A19).
  • A desk photograph is up to 10 MB in one POST — above the function payload ceilings (Vercel ~4.5 MB; Netlify ~6 MB sync), so the desk just sees “upload failed” on a phone. Uploads must become presigned object storage.
  • Serverless scales to many concurrent clones of the same function, each with its own in-process cache — on the file store the last writer wins and silently overwrites the other’s rows.
  • Admin auth is the one part that is serverless-proof: the session is a stateless signed cookie — no server session table, no sticky routing — and all 34 handlers are force-dynamic with no build-time data assumptions. The blocker is the disk, not the cookie.
  • Only /api/admin/media/upload declares runtime='nodejs' — it uses fs and cannot run on edge runtimes.

The five host-deciding constraints

1 · Persistent writable DBstore.ts file backend → needs a mounted DATA_DIR or Postgres. ✗ on pure serverless
2 · Uploads + public URLmedia/upload writes bytes then reads dimensions back → needs disk + a URL, or object storage
3 · Desk edits reach votersrevalidatePath only — no CDN purge API is wired; on a CDN the edge keeps serving until s-maxage expires
4 · 10 MB in one POSTMAX_BYTES 10 MB vs function payload caps 4.5–6 MB → the presigned-upload porting item
5 · Node runtime + Lagos vantagefs/crypto need Node (fine on function runtimes, not edge); users are in Lagos → edge CDN in front, origin London/Lagos

Mandatory post-deploy checks (§16)

  • The gate script against the production URL: BASE=https://… node scripts/check-cms-gates.mjs → 12/12.
  • The voter test: log out of the desk, fetch the page as a voter, confirm the new sentence is actually there. “Row 3 is the one teams get wrong” — the desk sees its edit immediately; the CDN may not.
  • Header verification after every deploy: curl -sI and grep strict-transport-security — a proxy can strip them silently, and the static export carries none at all.
  • Both DNS names (apex + www) resolve, redirect, and carry valid certificates.

What has not been decided

Status line, verbatim from the index: Verified locally as SSR. No production host assigned. [gap]

Every number in §10 was produced on 127.0.0.1:3100. CDN staleness, header stripping, ephemeral filesystems and TLS are unexercised. The recommendation on the record: ship a persistent server (B or C) for launch; run the Path-A port as scale-over work before the party-primaries-to-general-election window, because CDN-cached pages survive a rumour spike better than one origin. Budget line: choose flat-rate egress with overage tolerance over per-GB billing — a viral week on per-GB pricing is an invoice you discover after the fact.

What not to buy — and why, one line each

  • A bigger server instead of a CDN. A 1 vCPU origin behind Cloudflare out-performs a big box behind nothing; edge egress and photo disk are the constraints, never CPU.
  • Multiple app instances while still on the file store. No cross-process lock; silent lead loss plus a per-instance revalidation staleness machine.
  • Managed “WordPress-Next” hosting that cannot run a Node process. The app is a long-lived Node server with a writable disk; shared PHP/cPanel is architecturally impossible.
  • A serverless-only plan with nowhere persistent to write. It deletes your leads on redeploy (§6).
  • A separate image-resize service. The honest fix is object storage or edge optimisation — sharp was deliberately excluded (ADR-017); do not buy its way back in as a vendor.
  • A vendor dashboard that adds a second editing surface. The whole Live Desk argument is that a second UI is a thing to keep in sync, and it will drift.

§13 — STANDING REFUSALS

The refusals are a feature of the work

A checklist phase that “only ever gets ticked ‘no’” (12-CHECKLISTS Phase 5 · 06 Part E · PRD §12). Each was requested routinely by the category; each is excluded, most by architecture. Presenting them proudly is the point: this is what an honest system’s output looks like — including four empty frames on a live campaign site.

Refused in this build pass

  • Four evidence attachments were REFUSED rather than filled with plausible links — a6 indigent healthcare relief · a11 youth tournament sponsorship · a12 community vigilante/estate security · fc-accessible Truth Room ruling. None of the 21 references states them; the bar is the flagbearer precedent (the report names the party, office and constituency). They remain published, graded block, and the score stays 40.
  • Four photo frames are DELIBERATELY EMPTY rather than padded with stand-ins — family-portrait · hq-office · 23-road-inspection · community-security. All exact: a photograph of a different room cannot stand in for “the campaign’s office” — that is a factual claim wearing an image. The picker refuses to browse; the frame renders the branded panel until HQ supplies the actual photograph. The go-live checklist carries it as a task for a person with a camera.
  • No AI-generated portrait of the real candidate — anywhere, any form, including “upscales” and “restored” versions; the only generated graphics are explicitly non-portrait (mandate card, pillars, slogan) and labelled.
  • No invented rumour or fabricated verdict in the Truth Room — the ledger states only what a dated report states; harvesters refuse to caption a photo as showing the candidate unless the article puts him in it.
  • No publishing a claim the dossier does not attest with a source — the gate, in the mutation routes.
  • No deletion of the campaign’s existing data directories — “real leads die”; cleanup scripts may only remove records they created themselves; data/db.json is state, never configuration to reset.

Refused permanently (the full Phase-5 list)

  • Donation or payment page — C11’s ~270 fake donor-harvesting sites, plus unresolved Nigerian law on contributions for this office
  • Voter-roll import, name-matching, psychographic scoring — NDPA s.30; C22/C23 are what that ends in
  • Automated or scheduled posting to any platform; bulk WhatsApp initiated by the campaign — the WhatsApp link is clicked by the supporter, never sent unasked
  • Astroturfing, fake testimonials, incentivised reviews — Meta/CIB category since 2018, FTC rule since 2024, and 3.7 m accounts swept in this region in Oct 2026
  • AI-generated or AI-“restored” imagery of the candidate — constraint 1 + Art. 50 + a Nigerian prosecution
  • Generative drafting of captions, claims or verdicts — ADR-013; “⌘K parses; it does not draft”
  • Auto-publish from the War Room without a human pressing Save — human-in-the-loop as a property of the request graph
  • Scraping a rival’s site into “opposition research” — “the sort of thing that becomes the story about you”
  • A shared “god mode” login named per session; hand-editing the live store
  • A generic drag-and-drop page builder — “the layout is code because the layout is the argument”
  • Wholesale deletion of a user data directory

Discomfort named before someone else names it (06 Part D): the gate can be a weapon of delay — whoever holds the CMS can decide nothing is evidence. That is a governance problem: publish authority sits with a named person, findings are inspectable by a second one, and the rail’s output stays visible. And four empty frames plus a 40 score on a live site is the correct output of an honest system — worth more than a plausible wrong photograph.

§14 — GLOSSARY

Fourteen-plus terms, in the register this dossier uses them

Open/close the glossary
ISR · Incremental Static Regeneration
Prerendered pages that rebuild themselves on a timer: revalidate: 300/900/3600 per content page. Here it is an editorial staleness budget — the worst-case age of a public sentence.
Live Desk
The in-place editing overlay: the public page is the CMS when a valid session cookie is present. ⌘E reveal · tap-to-edit · ⌘K · ⌘Z. Zero DOM for anonymous visitors.
Publish gate
Server-side refusal, in the mutation routes, of any record/fact-check row created without an evidence link — and of any edit that empties one. EVIDENCE_RULE.
Integrity rail
The site’s self-audit: live-store scan → weighted, capped, grouped score + findings wired to the exact page and element. 40/100 at compilation.
Frame
A named media position (MEDIA_POSITIONS, 20 declared) with a fixed aspect ratio. exact frames accept only a real upload for that subject — never a library stand-in.
Attested
A claim a dated report in the 21-link reference library actually states. Attestation, not plausibility, is the publication bar.
Tombstone
An entry in db.removed recording a deliberate withdrawal, so a future content bundle or re-sync cannot resurrect the row. Deletions are remembered.
Resync
resyncSeeds() on a changed SEED_VERSION: refresh bundle-owned rows, keep every desk-created row, never touch volunteers or inquiries. A redeploy is not a data-loss event.
revalidatePath
Next.js invalidation of the server-side cache for one route after a write. Behind a CDN it does not touch the edge copy — that needs a vendor purge, which is not wired. src/lib/revalidate.ts is the registry every new page must enter.
oEmbed
The provider lookup (YouTube here) that confirms a video id exists and permits embedding, returning title and author server-side, with a 6-second abort. What makes “7 clips” mean verified clips.
Service-role key
SUPABASE_SERVICE_ROLE_KEY — the write credential, bypassing row-level security. Never a NEXT_PUBLIC_* value, never a build-time secret on a shared runner; a runtime secret to be rotated.
RLS · Row-Level Security
Database policies that mirror the app’s toPublic() stripping — reporter name/phone/consent absent from any anon-key read even if a handler forgets. The guarantee does not depend on the handler.
DSR · Data-subject request
Confirmation, access, copy, rectification, erasure, restriction (NDPA s.34). Fulfilment here is manual through the CMS — locate, act, purge the orphaned upload, record the date — via runbook 7.10.
HITL · Human-in-the-loop
No route publishes on a timer, webhook or model judgement alone. A War Room draft needs a person to press Save. Structural, not procedural.
Core Web Vitals
LCP ≤ 2.5 s · INP ≤ 200 ms · CLS ≤ 0.1 at p75 of field data (web.dev). NFR-8 adopts them plus an internal TTFB budget (< 600 ms cached / < 1.2 s uncached p75) labelled as internal — with zero field measurement taken over a real Nigerian mobile connection [gap].
data-ow
The single annotation attribute that makes a rendered value editable — "settings.hero_title", "record.a12.verification_source_url", "slot.hq-office". A field becomes editable the moment it carries one; 38 sites today.
